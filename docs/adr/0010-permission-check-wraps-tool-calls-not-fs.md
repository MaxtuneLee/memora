# Permission check wraps tool calls, not `@memora/fs`

Chat tools declare an Access request (the library files, search scope, or path they will read or write) and `createChatTools` checks it before running the tool body: Reference scope for reads, then Permission grants, then the approver from the Permission mode (the user, or Auto review that hands unsure cases back to the user). A denial comes back to the agent as a tool error.

We check at the tool call instead of inside `@memora/fs` because only the tool knows what a call means. A library-wide search reads every file through snippets but touches the filesystem through one `grep`; `read_extracted_content` reads a derived artifact that belongs to a library file; `create_document` writes a file that does not exist yet into a folder; the document editor tools touch a note through the editor, not OPFS. A filesystem hook would see paths without that meaning, would ask once per file for one search, and would also gate the app's own reads (indexing, previews, the session store). Declaring the request with each tool keeps one place to review when a tool is added; the cost is that a tool which forgets to declare one is not guarded, which the tests over `createChatTools` cover.

Grants are saved with the other user settings and match through the live folder tree, so moving a file or folder keeps or drops access the way the tree says. Auto review sees only the user's messages in the current Run, the tool name and parameters without written content, and the request's names and types, never file content, so text planted in a file cannot steer it; its decisions are never saved as grants.
