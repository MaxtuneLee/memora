# GPT-6 Luna 的 Chat Completions 与输出上限调查

调查日期：2026-10-17。用户已确认模型 ID 为 `gpt-6-luna`。基线为 `origin/main` 的 `8c32a88`，调查分支为 `codex/investigate-luna-chat`。

## 后续实现

本分支现已按用户要求改用 models.dev，产品代码不再查询 pi 的模型目录。构建插件会从 `https://models.dev/api.json` 获取目录，只保留 Memora 所需的公开元数据并打入独立静态模块；开发和构建获取失败时使用仓库中的 `packages/web/models-dev.snapshot.json`。运行时先查静态缓存，缺少模型时拉取最新目录，同一轮并发查询共享请求，成功或失败后对缺项刷新保留 5 分钟间隔。

发现解析会补全上下文、输出上限、名称、思考能力、输入模态、基础价格和思考级别映射；供应商明确返回的值逐字段优先。按供应商端点匹配，未知网关优先使用模型原供应商记录，无法判定归属的重复 ID 不混用其他供应商限制。目录请求不携带供应商 API key。

请求构造检查已整理为 `packages/ai-provider/pi/test/lunaMetadata.test.mjs`，使用 models.dev 快照并作为正式回归测试运行；已确认 Luna 默认带 function 的请求包含 `reasoning_effort: "none"` 和 `max_completion_tokens: 128000`。下文保留原始 `8c32a88` 基线的调查记录。已有供应商模型记录在重新加载模型列表后更新；用户显式提供的上限不被覆盖。显式 high + function 的官方 Chat Completions 限制仍需使用 Responses。

## 结论

GPT-6 Luna 在 Chat Completions 中调用 function 必须显式使用 `reasoning_effort: "none"`；需要思考和工具一起工作时，应使用 Responses API。这是官方接口限制。Luna 默认思考级别为 `medium`，省略参数不能代表关闭思考。官方上限为 1,050,000 的上下文和 128,000 的输出 tokens。[官方模型页](https://developers.openai.com/api/docs/models/gpt-6-luna)、[官方迁移说明](https://developers.openai.com/api/docs/guides/latest-model)。

当前 Memora 的默认请求恰好会省略 `reasoning_effort`，同时传入工具。对官方约束而言，这个组合不兼容。输出上限 4096 则来自本地模型元数据的兜底值；本地捕获确认最终请求确实发送了 `max_completion_tokens: 4096`。

初次调查只添加了调查文档和本地复现脚本；后续产品改动见上方「后续实现」。没有调用付费接口或读取用户凭据；请求在 pi-ai 完成 payload 构造后由 `onPayload` 主动中断，并额外阻止网络访问。因此确认的是请求与官方文档之间的冲突，未捕获用户实际遇到的服务器错误或真实输出截断。

## 为什么省略了关闭思考的参数

1. 模型发现调用 `${endpoint}/models`，然后由 `parseProviderModel` 解析。OpenAI 的模型对象没有思考能力或 `thinkingLevelMap` 字段，因此解析结果为 `reasoning: false`，且没有关闭思考的映射。参见 [providerModels.ts](../../packages/web/src/lib/settings/providerModels.ts)、[dialogHelpers.ts](../../packages/web/src/lib/settings/dialogHelpers.ts)。
2. `loadPiModelLimits()` 只从 pi-ai 目录补全 `contextWindow` 和 `maxTokens`，不会补全 `reasoning`、`thinkingLevelMap`、输入模态或其他接口能力。参见 [AI provider](../../packages/ai-provider/pi/src/index.ts)。
3. 主对话的 `AgentLoop.think()` 传入全部已注册工具，默认没有传入思考级别。`useChatModelConfig` 保留供应商选择的 API 格式，未配置格式时默认使用 `chat-completions`，没有模型级别的兼容检查。参见 [loop.ts](../../packages/ai-core/src/loop.ts)、[useChatModelConfig.ts](../../packages/web/src/components/chat/chatPage/useChatModelConfig.ts)。
4. pi-ai 的 Chat Completions 构造器只有在 `model.reasoning` 为真且 `thinkingLevelMap.off` 是字符串时，才会在未指定思考级别时发送对应的关闭值。当前元数据不满足这两个条件，最终省略 `reasoning_effort`。代码位于已安装的 `@earendil-works/pi-ai/dist/api/openai-completions.js`。

因此，当前主对话路径不需要用户主动选择 high 等思考级别就能触发问题。省略参数后，官方默认 `medium` 与 function 调用的限制已经冲突。即使仅把 `reasoning` 改成 true，也仍然缺少 `off: "none"`，不能解决默认请求的问题。

## 为什么输出上限只有 4096

官方 `GET /models` 和 `GET /models/{model}` 的模型对象返回身份、创建时间、归属等基础字段，不返回上下文或最大输出 tokens。增加一次模型详情请求也无法从该标准接口取得这些上限。[官方模型对象定义](https://developers.openai.com/api/reference/resources/models/methods/retrieve)。

Memora 已有目录补全过程，其优先级为供应商发现字段 → pi-ai 静态目录 → 本地默认值。但是当前锁定的 `@earendil-works/pi-ai@0.87.0` 目录没有精确 ID `gpt-6-luna`，所以仍然落到 `contextWindow: 131072` 和 `maxTokens: 4096`。目录中存在 `gpt-5.6-luna`，其输出上限为 128000，这不能自动匹配到 GPT-6 Luna。

`useChatModelConfig` 对选中但未匹配到元数据的模型还有一套相同的 4096 兜底值。普通主对话没有额外指定 `maxTokens`，pi-ai 因此沿用 `model.maxTokens`，转换成正确的 Chat Completions 字段 `max_completion_tokens`。本次未发现把 `max_tokens` 错用于 Luna 的情况。

另外存在两个会让限制继续偏小的路径：

- `parseProviderModels()` 读取已保存配置时没有传入目录查询函数；已保存的 4096 会继续被使用。以后更新目录还需要刷新模型元数据或做有来源信息的迁移。
- `loadPiModelLimits()` 按模型 ID 跨供应商合并并取最小值，可能把供应商特定的上下文限制用于其他供应商。对 GPT-6 Luna 的 4096 问题，直接原因仍是目录缺项。后续应按供应商和 API 格式区分查询。

pi-ai 还会按剩余上下文缩小每次请求的输出预算：`min(requestedMaxTokens, max(1, contextWindow - estimatedInputTokens - 4096))`。本次使用很短的输入仍发出 4096，已排除该场景中因长输入导致上限变小。错误的 131072 上下文元数据也可能让长对话提前压缩。

`max_completion_tokens` 包含思考和可见输出等生成 tokens。即使请求上限为 4096，可见文字也可能更少；需要真实响应的 usage 和 finish reason 才能确认某次输出是否因此截断。[官方 token 说明](https://developers.openai.com/api/docs/guides/token-counting)。标题生成的 24 tokens 和 Auto review 的 200 tokens 属于独立调用，不是主对话的输出上限。

## 本地捕获结果

使用真实的 Memora `createRemotePiRuntime` 和 pi-ai 请求构造器。每次最多传入一个空参数 function，且不发出 HTTP 请求。

| 场景 | 请求格式 | 思考字段 | 工具数 | 输出预算 |
| --- | --- | --- | --- | --- |
| 当前发现结果、主对话默认参数 | Chat Completions | 省略 | 1 | 4096 |
| 当前发现结果、调用者请求 high | Chat Completions | 省略（reasoning 为 false） | 1 | 4096 |
| 仅修正输出与上下文上限 | Chat Completions | 省略 | 1 | 128000 |
| 仅修正 reasoning 为 true | Chat Completions | 省略（仍缺少 off 映射） | 1 | 4096 |
| 修正元数据、显式 high | Chat Completions | reasoning_effort: high | 1 | 128000 |
| 修正元数据和 off 映射、默认参数 | Chat Completions | reasoning_effort: none | 1 | 128000 |
| 修正元数据、显式 high | Responses | reasoning.effort: high | 1 | 128000 |
| 修正元数据、显式 high、移除工具 | Chat Completions | reasoning_effort: high | 0 | 128000 |

后两类兼容组合已验证请求形状，尚未进行官方 API 联调。Chat Completions 的 high + function 组合即使修正 token 上限也仍然违反官方限制。

## 建议修复顺序

1. 对官方 OpenAI 的 GPT-6 Luna 提供带来源的准确模型元数据：上下文 1050000、输出 128000、支持思考、正确的思考级别和 `off: "none"`。补全应区分供应商，避免对任意兼容网关直接假设官方能力。升级 pi-ai 前应先确认新目录是否已经包含该模型，升级本身也无法替代端点组合校验。
2. 默认 Chat Completions + function 调用明确发送 `reasoning_effort: "none"`。用户需要思考时走已实现的 Responses 适配器，或在配置中明确提示需切换；不要静默丢弃用户选择的思考级别。Responses 也需要正确元数据，否则请求仍会保留 4096 上限且显式 high 可能被忽略。
3. 完善元数据补全，涵盖思考能力和参数映射。为发现结果和已保存模型记录保留来源或版本信息，区分真实供应商上限、用户指定预算及本地兜底值，再刷新旧记录。避免无条件覆盖用户设置或供应商明确给出的较小值。
4. 在真实请求构造层补回归检查，覆盖默认 Chat + function、显式思考 + function、Responses + function、新模型缺目录和已保存旧上限，并补一次官方 API 联调。
